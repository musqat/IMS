## 배포가 14분 만에 타임아웃됐다

`문제`
Render 배포가 실패했다. 로그는 `Root WebApplicationContext: initialization completed`
에서 멈춰 있고 그 뒤로 아무것도 없다.

```
Port scan timeout reached, no open ports detected
```

`원인`
처음엔 DB가 슬립됐다고 봤다. 그런데 Supabase 로그를 보니 11:51 UTC에 애플리케이션이
아직 DDL을 실행하고 있었다. Render는 11:50에 포기했다.

**멈춘 게 아니라 느린 것이었다.** 무료 티어의 낮은 CPU에서 JVM 기동과 `ddl-auto` 검사가
겹치면 포트 스캔 한도를 넘긴다.

`해결`
재배포하니 157초에 떴다. 같은 코드, 같은 설정이다.

원인을 잘못 짚었던 게 더 남는다. "멈췄다"와 "느리다"는 로그가 같은 자리에서 끊겨서
구분이 안 됐고, DB 쪽 로그를 보고서야 갈렸다. **한쪽 로그만 보고 판정하면 안 된다.**

## 자정 배치가 오전 9시에 돌았다

`문제`
전날 PENDING을 결산하는 배치가 의도한 시각에 안 돌았다.

`원인`

```java
@Scheduled(cron = "0 5 0 * * *")   // zone 미지정
```

Dockerfile에 `TZ`도 없어 컨테이너가 UTC로 돈다.

```
의도   00:05 KST
실제   00:05 UTC = 09:05 KST
```

`해결`
`zone = "Asia/Seoul"` 을 명시했다. Dockerfile의 `TZ`로 맞추는 방법도 있는데 이쪽을 골랐다.
**코드에 의도가 남고 호스트 설정에 의존하지 않는다.**

같은 배치에서 두 가지를 더 손봤다. 한 건이 실패하면 나머지가 같이 롤백되던 것을 건별
`REQUIRES_NEW`로 분리했고, 중복 실행을 막으려고 JobParameters에 날짜를 넣었다.

## KPI 숫자를 눌렀더니 빈 화면

`문제`
대시보드의 "확인 필요 20건"을 눌렀더니 생산 기록 페이지가 비어 있었다. 숫자는 맞는데
목록이 없다.

`원인`
KPI가 세는 축과 페이지 탭의 축이 달랐다.

```
KPI      결산 결과   SUCCESS / ANOMALY / FAILED
페이지 탭  생산 상태   PENDING / SETTLED / CANCELLED
```

"확인 필요"는 `ANOMALY`를 센 건데, 링크가 걸린 탭에는 `ANOMALY`라는 상태가 없다.
양쪽 다 각자는 맞다. 이어붙인 곳이 어긋났다.

`해결`
결산 결과로 필터되는 탭을 만들고 KPI가 그쪽을 가리키게 했다.

같은 화면에서 하나 더 나왔다. 대시보드 KPI가 전부 0으로 나오던 문제다.

```java
public int total() { return settled + pending + cancelled; }
```

Jackson은 record의 컴포넌트를 직렬화한다. 파생 메서드는 JSON에 안 실린다.
`pending`·`anomaly`는 컴포넌트라 정상이었고 `total`만 0이었다.

## 삭제하려는데 "이미 존재한다"고 나왔다

`문제`
재고가 있는 창고를 지우려 하면 이 메시지가 나왔다.

```
409  이미 존재하는 리소스입니다
```

삭제 요청에 "이미 존재한다"는 답이라 무슨 말인지 알 수 없다.

`원인`
`WarehouseService.delete` 가 참조 무결성을 확인하지 않고 그냥 삭제를 시도했다.
DB가 FK 위반을 던지고, `GlobalExceptionHandler` 가 그걸 `DataIntegrityViolationException`
으로 받아 `DUPLICATE_RESOURCE` 로 매핑했다. 제약 위반이라는 점만 같고 원인은 전혀 다르다.

`해결`
삭제 전에 참조를 직접 확인하도록 바꿨다. 재고·생산 기록이 있으면 거부하고 이유를 말한다.
공유 설정은 함께 삭제한다.

그런데 고치고 나니 기능이 닫혀 있다는 게 드러났다. 재고가 있는 창고는 사실상 영영 못 지운다.
재고와 생산 기록은 분석의 원본이라 함께 지울 수도 없다. `active` 플래그로 비활성화하는
경로를 따로 만들었다.

<br>

## 기동이 not-null 위반으로 죽었다

`문제`
`Warehouse.active` 를 추가한 뒤 시드 적재에서 기동이 실패했다.

`원인`
기본값을 `@Builder.Default` 로만 걸었다. 이건 자바 빌더를 탈 때만 적용된다.
`seed.sql` 은 순수 SQL INSERT라 그 경로를 안 탄다.

`해결`
`columnDefinition` 으로 DB 기본값을 함께 지정했다. 엔티티 기본값과 DB 기본값이 둘 다
필요하다.

같은 시드에서 한글이 깨진 적도 있다. `ScriptUtils.executeSqlScript` 가 파일을 플랫폼 기본
문자셋으로 읽는데 한국어 윈도우는 MS949다.

```java
new EncodedResource(new ClassPathResource("seed.sql"), StandardCharsets.UTF_8)
```

**리눅스는 기본이 UTF-8이라 배포 환경에서는 안 나타난다.** 로컬에서만 나는 문제였고,
그래서 한 번은 콘솔 인코딩 탓으로 넘겼다가 다시 잡았다.

<br>

## 목록이 다른 목록에 오염됐다

`문제`
생산 기록 페이지에서 탭을 옮기면 항목 수가 이상하게 나왔다.

`원인`
React Query 캐시 키에 `size` 가 빠져 있었다.

```
byStatus(status, page)        ← size 없음
```

대시보드는 5건씩, 목록 페이지는 20건씩 같은 상태를 조회한다. 키가 같으니 서로의 응답을
가져다 썼다.

`해결`
키에 `size` 를 넣었다. 캐시 키는 **요청을 유일하게 식별해야 한다.** 파라미터 하나가
빠지면 그만큼 다른 요청이 같은 것으로 취급된다.

<br>

## CI 첫 실행이 Permission denied

`문제`
CI를 처음 붙였더니 백엔드 잡의 첫 스텝이 죽었다.

`원인`

```
git ls-files -s backend/gradlew
100644 ...   ← 실행 비트 없음
```

`해결`

```bash
git update-index --chmod=+x backend/gradlew
```

**Windows에서는 실행 비트가 무의미해서 로컬 테스트로는 절대 안 걸린다.** CI를 붙이는
행위 자체가 이걸 드러냈다.

같은 실행에서 `npm audit` 도 처음 돌려 봤다. 20건(high 13)이 나왔는데 대부분 전이 의존성이다.
CI에는 안 넣었다. 첫날부터 빨간불이면 신호가 아니라 배경이 된다.

<br>

## 비밀번호 `123456` 이 가입됐다

`문제`
격리 스택에 실제 회원가입 요청을 보내 확인했다.

| 비밀번호 | 응답 |
|---|---|
| `123456` | 201 |
| `aaaaaa` | 201 |
| `password` | 201 |
| `12345678` | 201 |

`원인`
정책이 `@Size(min = 6)` 하나뿐이었다.

`해결`
8자 이상 + 영문·숫자 혼용으로 바꿨다. 위 네 개가 전부 400이 된다. 프론트 zod 스키마도
같은 규칙으로 맞췄다. 한쪽만 고치면 화면과 서버가 다른 말을 한다.

같은 점검에서 `Pageable` 상한도 나왔다. `size=999999` 가 2000에서 막히긴 하는데, 그 2000이
Spring Boot 기본값이라 코드에 명시한 방어가 아니었다. `application.yml` 에 적었다.

<br>

## 409가 열 가지 원인을 가린다

`문제`
프론트가 409를 받아도 무엇 때문인지 알 수 없었다. 응답에 HTTP 상태와 메시지만 있고
식별자가 없다.

`원인`
`ApiResponse.fail(ErrorCode)` 가 `ErrorCode` 에서 메시지만 꺼내고 이름을 버렸다.
409를 쓰는 `ErrorCode` 가 열 개가 넘어서 상태 코드로는 원인을 못 가른다.

`해결`
응답에 `code` 를 추가했다.

```java
public record ApiResponse<T>(String code, String message, T data)
```

`SecurityConfig` 의 필터 단계 401도 문자열 조립 대신 같은 직렬화를 타게 바꿨다.
소비처로 창고 삭제 실패 시 비활성화를 제안하는 화면을 붙였다. **응답에 코드가 있으니
프론트가 원인별로 다르게 행동할 수 있다.**
