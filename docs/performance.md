# 성능 튜닝

조회 경로의 쿼리 수를 쟀다. 쿼리 수는 머신 속도와 무관하고 같은 조건이면 같은 값이 나온다.
"3.2초 → 0.8초"는 잰 기계가 바뀌면 못 쓴다.

측정은 `QueryCountTest`가 한다. Hibernate `Statistics`의 `getPrepareStatementCount()`로
서비스 호출 전후 차이를 센다. 데이터 규모를 바꿔가며 두 번 재서 **쿼리 수가 규모에
비례해 늘지 않는지**를 본다.

## 잰 결과

조건은 H2, 창고 1개, 단일 소유자다.

| 경로 | 작은 규모 | 큰 규모 | 최적화 제거 시 |
|---|---|---|---|
| 재고 목록 | 품목 5개 → **2** | 품목 50개 → **2** | 품목 50개 → **52** |
| 부족 분석 | 완성품 1개 → **6** | 완성품 20개 → **6** | — |
| 최대 생산량 | BOM 부품 3개 → **5** | BOM 부품 30개 → **5** | — |

재고 목록과 최대 생산량은 10배, 부족 분석은 20배로 늘렸다. 세 경로 모두 쿼리 수가 같다.

<br>

## 재고 목록 — 품목 수만큼 쿼리가 늘었다

`InventoryResponse`가 품목 코드·이름·타입을 읽는다. `Inventory.item`이 LAZY라
행마다 품목 조회가 따라붙는다.

```
                    품목 5개   품목 50개
@EntityGraph 없음        7        52
@EntityGraph 있음        2         2
```

50개에서 52개는 목록 1회 + 카운트 1회 + 품목 50회다. 품목이 늘어나는 만큼 그대로 늘어난다.

```java
@Override
@EntityGraph(attributePaths = {"item"})
Page<Inventory> findAll(Specification<Inventory> spec, Pageable pageable);
```

한 줄로 52개가 2개가 된다. 남은 2개는 목록과 카운트다.

같은 방식으로 리포지토리 6개에 `@EntityGraph` 12곳을 붙였다.
연관은 전부 LAZY고 `FetchType.EAGER`는 한 곳도 없다.

## 부족 분석 — 완성품 20개에 6개

완성품마다 BOM을 타고 부품 재고를 확인한다. 제품별로 조회하면 완성품 수만큼 쿼리가 나간다.

```
완성품  1개  →  6
완성품 20개  →  6
```

부품 아이디를 전부 모은 뒤 `IN` 절로 한 번에 조회한다.

```java
Set<Long> allPartIds = allBomTrees.values().stream()
        .flatMap(requirements -> requirements.keySet().stream())
        .collect(Collectors.toSet());

Map<Long, Integer> stockMap = inventoryRepository
        .findAllByWarehouseIdAndItemIdIn(warehouseId, List.copyOf(allPartIds))
        ...
```

부족 부품의 상세 정보도 같은 방식으로 한 번에 받는다.

6개의 내역은 접근 권한 2회(창고·공유 설정)와 분석 4회(완성품 목록 / BOM 인접 리스트 /
부품 재고 / 부족 부품 정보)다. 코드 주석이 "4회로 고정"이라고 적혀 있었는데 그건 권한
확인을 뺀 값이다.

<br>

## 최대 생산량 — BOM 부품 30개에 5개

BOM 트리를 재귀로 돌면서 노드마다 자식을 조회하면 노드 수만큼 쿼리가 나간다.

```
BOM 부품  3개  →  5
BOM 부품 30개  →  5
```

인접 리스트를 한 번에 로드한 뒤 인메모리 DFS로 돈다. 탐색 중에는 쿼리가 나가지 않는다.
서브트리 결과는 메서드 지역 `HashMap`에 담아 같은 노드를 두 번 돌지 않는다.

이 캐시를 Redis에 올리는 안도 검토했다. BOM이 하나 바뀌면 그 품목을 포함하는 상위 트리를
전부 지워야 하고, 그 역추적 비용이 재계산보다 컸다. 요청 단위로만 유효하면 충분한
성격이라 지역 맵으로 뒀다. Redis는 리프레시 토큰 저장에만 쓴다.

<br>

## 고정을 확인하는 방법

테스트가 두 규모에서 재고 값이 같은지 단언한다.

```java
long withFiveItems  = countQueries(() -> inventoryService.getInventories(...));  // 품목 5개
long withFiftyItems = countQueries(() -> inventoryService.getInventories(...));  // 품목 50개
assertThat(withFiftyItems).isEqualTo(withFiveItems);
```

절대값을 박지 않고 **두 규모의 값이 같은지**만 본다. 절대값을 박으면 권한 확인 쿼리
하나가 늘어날 때마다 테스트를 고쳐야 하고, 그러다 보면 N+1이 섞여 들어와도 숫자만
맞춰놓게 된다.

제대로 짰는지는 최적화를 떼서 확인했다.

```
@EntityGraph 제거   →   품목 50개에서 52개.  테스트 실패
원복                →   2개.  통과
```

동시성 락을 검증할 때와 같은 방식이다. 통과하는 걸 보는 것만으로는 그 테스트가
무엇을 막고 있는지 알 수 없다.

## 안 잰 것

**응답 시간** — 무료 인스턴스에 올라가 있어 콜드 스타트와 CPU 공유로 값이 흔들린다.
같은 요청을 재도 편차가 커서 비교 기준이 못 된다.

**부하** — 동시 사용자를 늘려가며 재지 않았다. 데모 규모라 부하가 병목이 되는 지점까지
가지 않는다.

**인덱스** — 복합 유니크 제약이 인덱스 역할을 하지만 실행 계획을 따로 보지 않았다.
`EXPLAIN`으로 확인한 기록이 없다.

**결산 배치** — 생산 기록 수를 늘려가며 쿼리 수를 재지 않았다. 부품 재고를 `IN` 절로
일괄 조회하고 건별로 트랜잭션을 나누는데, 그 조합에서 건당 쿼리가 몇 개인지는 안 봤다.

**JVM 메모리는 쟀다.** `docker run -m 512m`에서 힙 360MB, 기동 5.3초, 부하 후
311MB/512MB, OOM 없음. `-XX:MaxRAMPercentage=70`을 이미지에 넣어 확인한 값이다.
