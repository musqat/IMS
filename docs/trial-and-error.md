무엇을 될 거라 봤고 무엇으로 갈렸는지를 남긴다.

확인 방법은 하나로 통일했다. **코드를 읽어서 판단하지 않고 실제로 돌려본다.**

## 확인해보니 반대였던 것

| 예상 | 확인 결과 |
|---|---|
| 커버리지 92%면 결함은 거의 안 남는다 | 배포 후 14건. 그중 단위 테스트가 찾은 건 0건 |
| 권한 체크를 만들고 테스트가 통과하면 화면에서도 동작한다 | 프로덕션 호출이 0건이었다. FULL이 VIEW와 같았다 |
| 동시성 테스트가 통과하니 락은 걸려 있다 | 테스트가 서비스를 안 탔다. 락을 떼도 통과했다 |
| 창고 주인이 그 안 품목의 주인이다 | 물류 창고는 남의 물건을 보관만 한다. 다른 게 정상이었다 |
| 화면이 비면 데이터가 없는 것이다 | 조회가 500이어도 똑같이 빈다 |
| 만료된 초대는 중복으로 막으면 된다 | UK 때문에 그 관계는 영영 초대 불가가 된다 |
| Testcontainers를 붙이면 실제 DB로 테스트할 수 있다 | 안 붙여도 된다. 컨테이너를 미리 띄우면 JDBC만 남는다 |

## 테스트가 통과해도 프로덕션은 그 코드를 안 부른다

README가 창고 공유를 `VIEW` / `FULL` 두 단계로 소개하고 있었다. 구현도 있고 단위 테스트도
통과한다. 그런데 호출처를 세어 보니 이랬다.

```
checkFullAccess 호출처
  WarehouseShareServiceTest 뿐
```

프로덕션 호출이 0건이다. 재고 쓰기 경로가 전부 소유자 전용 헬퍼를 쓰고 있었다.
**FULL 권한을 받아도 VIEW와 아무 차이가 없다.** 기능이 없는 걸 README가 있다고 말하고
있었던 셈이다.

단위 테스트로는 이 유형이 안 잡힌다. 테스트가 그 함수를 **직접** 부르기 때문에,
프로덕션이 부르는지는 처음부터 검증 대상이 아니다.

배선한 뒤 실제로 쳐서 확인했다.

```
FULL 입고        200, 재고 480 → 490
FULL 창고 삭제    403
FULL 재고 등록    403
VIEW 입고        403, 재고 불변
```

같은 방식으로 다른 함수도 세어 봤다. `cancelInvite`가 하나 더 나왔다 — 초대 취소를
만들어 놓고 화면에 버튼이 없었다.

<br>

## 테스트를 고치자 프로덕션 결함이 나왔다

동시성 테스트가 있었고 통과하고 있었다. 그런데 읽어 보니 리포지토리를 직접 부르고
서비스 로직을 타지 않았다. **락을 떼도 통과하는 테스트였다.**

서비스를 타게 고치자마자 프로덕션 결함이 드러났다.

```
findAllByWarehouseIdAndItemIdInForUpdate 사용처
  SettlementService  ← 여기 하나뿐
```

결산은 락을 걸었는데 출고(`adjustOut`)는 락 없는 조회를 쓰고 있었다. `@Version`도 없어
낙관적 락도 안 걸린다.

재고 10에서 3씩 6스레드가 동시에 나가면 이렇게 된다.

```
6개 전부 재고 10을 읽는다
6개 전부 "10 - 3 = 7, 통과" 판정      ← 각자 낡은 값으로 검사
DB 재고     7
실제 출고   18
검산        10 + (-18) = -8  ≠  7
```

재고가 음수로 가지는 않는다. 도메인 가드가 막는다. 대신 **실제보다 크게 남는다.
없는 재고를 있다고 보고한다.**

더 위험한 건 자정 배치와의 경합이었다. PostgreSQL MVCC에서 일반 SELECT는 `FOR UPDATE`에
막히지 않으므로, 결산이 차감한 재고를 출고가 덮어쓸 수 있었다.

락을 떼고 다시 돌려 확인했다.

```
락 있음   통과
락 제거   expected: 3, but was: 6
          expected: 7, but was: -8
```

두 번째 숫자가 손으로 계산한 `10 + (-18) = -8`과 맞는다.

나중에 H2가 아닌 실제 PostgreSQL에서도 같은 방식으로 재확인했다. H2는 `MODE=PostgreSQL`
이어도 락 의미론이 달라서 이 검증에는 부족하다.

## 창고 주인이 품목 주인일 줄 알았다

공유받은 창고의 상세 화면에서 제목이 `...`로 나왔다. 네트워크 탭을 보니 셋이 깨져 있었다.

```
max-producible      403 (ITEM_NOT_OWNED)
shortage-analysis   에러가 아니라 조용히 0건
GET /warehouses/{id} 소유자 전용이라 이름을 못 읽음
```

"품목은 창고 소유자 기준으로 조회한다"가 어긋났다.

```
이스마트 서울창고
  창고 주인  = 이스마트코리아 (유통사)
  안의 재고  = 아이테크조립의 완성품
```

물류·유통 창고는 남의 품목을 보관만 한다. **창고 소유자와 품목 소유자가 다른 게 오히려
정상이다.** 코딩 실수가 아니라 도메인을 잘못 읽은 것이었다.

시드 데이터로 화면을 대조했다.

| | 전 | 후 |
|---|---|---|
| 대시보드 창고 수 | 4 (소유만) | 10 (소유 4 + 공유 6) |
| 공유 창고 부족 분석 | "이상 없음" | 5개 품목 부족 |
| 공유 창고 max-producible | 403 | 200 |
| 소유 창고 max-producible | 7 | 7 (변화 없음) |

마지막 줄을 같이 잰 이유는, 고치면서 기존 동작을 안 건드렸다는 걸 보여야 해서다.

## 빈 화면은 두 가지를 뜻한다

```tsx
const { data: received = [] } = useReceivedInvites();
```

기본값 `[]` 때문에 조회가 500이어도 빈 배열이 된다. 수신함은 0건이면 섹션을 안 그리므로
화면이 **"초대 없음"과 완전히 같아진다.**

상대는 보냈다고 하는데 내 화면에는 아무것도 없는 상황이 여기서 만들어진다. 사용자도
개발자도 실패를 모른다.

백엔드를 실제로 내리고 새로고침해서 확인했다.

```
전   화면이 텅 빈다
후   "초대 목록을 불러오지 못했습니다" + 재시도 버튼
```

백엔드를 다시 올리자 React Query가 스스로 복구했다.

판정에 5xx만 보면 부족했다. **서버에 닿지 못한 경우**(`isPending` + `fetchStatus: 'paused'`)
도 같이 잡아야 한다. 무료 인스턴스 콜드 스타트가 정확히 그 상태다.

## 제약을 지키려다 기능을 영영 막았다

Partnership의 UK가 `(main_id, sub_id)`다. 초대 토큰에 만료를 넣으면서 문제가 생겼다.
만료된 초대를 그냥 "중복"으로 막으면 UK 때문에 새 행을 만들 수 없어 **그 관계는 다시는
초대할 수 없게 된다.**

기존 행의 토큰과 만료 시각을 재발급하는 쪽으로 처리했다.

| 기존 행 | 처리 |
|---|---|
| ACCEPTED | 중복 |
| PENDING, 유효 | 중복 |
| PENDING, 만료 | 재발급 (같은 id) |

창고 삭제에도 같은 모양이 있었다. 재고나 생산 기록이 있으면 물리 삭제가 막히는데, 둘 다
분석의 원본이라 함께 지울 수 없다. 결과적으로 삭제 기능이 닫혀 있었다. `active` 플래그로
비활성화하되 **조회 경로는 통과시킨다.** 비활성화했다고 지난 이력이 안 보이면 흐름 분석이
끊긴다.

<br>

## 도구를 바꾸지 않고 문제를 없앴다

동시성 테스트를 실제 PostgreSQL에서 돌리려고 Testcontainers를 넣었다. 로컬 Docker Desktop이
`/info` 요청에 400을 돌려주며 붙지 않았다.

컨텍스트 자동 감지, `DOCKER_HOST` 두 종류 파이프, `DOCKER_API_VERSION` 네 가지, 라이브러리
상향. 전부 400이었다.

여기서 방향을 바꿨다. **컨테이너를 테스트가 띄울 필요가 없다.**

```
Testcontainers   테스트 → Docker API → 컨테이너 → JDBC   (API에서 막힘)
채택한 방식       미리 띄운 컨테이너            → JDBC   (JDBC만)
```

테스트 DB 설정을 환경변수로 덮게 하고 별도 Gradle 태스크를 뒀다. 기본 `test`는 H2 그대로다.
CI는 리눅스 러너라 `services:`로 붙어서 이 문제 자체가 없다.

도구를 고치는 데 시간을 더 쓸 수도 있었다. 그런데 그 도구가 하려던 일(컨테이너 띄우기)을
빼면 문제도 같이 사라진다.

<br>

## 하지 않기로 한 것

**창고 간 비교 뷰** — `InventoryHistory`에 출고처가 없어 총량 비교가 의미를 못 갖는다.
하려면 거래처 모델링부터 필요하다. 재고 소진 예측으로 대체했다.

**보충 판정 사슬** — 이 시스템의 범위는 창고 간 입출고 흐름 분석이고 소진 예측이 그 끝이다.
"3개월 남았다"까지 내면 충분하다. 그 뒤(생산처에 완제품이 있나 → BOM으로 만들 수 있나)는
생산 계획 영역이라 다른 시스템이다.

**초대 재발송** — 이메일 인증처럼 재발송 버튼을 붙일까 검토했다. 그런데 이 시스템의 초대는
전달 경로가 없다. 토큰을 만들어 화면에 띄우고 사용자가 직접 전달한다. **유실될 구간이
없으니 재처리할 것도 없다.** 대신 만료된 초대의 토큰 재발급만 넣었다.

셋 다 "할 수 있는데 안 한 것"이다. 범위를 넓히는 쪽이 늘 나은 건 아니라고 봤다.

## 배운 점

**커버리지는 결함이 없다는 뜻이 아니다.** 327개 테스트, 라인 92%인 상태에서 결함 14건이
나왔고 그중 단위 테스트가 찾은 건 0건이다. 기존 테스트는 회귀를 막았지 새 결함을 찾지는
않았다.

**구현했다와 연결했다는 다르다.** 권한 체크도 초대 취소도 구현과 테스트는 있는데 프로덕션
호출이 0건이었다. 새 함수를 만들면 호출처를 세어 본다.

**테스트가 통과하는 것과 테스트가 검증하는 것은 다르다.** 동시성 테스트는 서비스를 안 타서
락을 떼도 통과했다. 고친 곳을 일부러 되돌려서 테스트가 실패하는지 본다.

**실패는 눈에 보여야 한다.** 조회 실패가 "데이터 없음"으로 흘러가면 아무도 모른다.
기본값으로 빈 배열을 주는 자리마다 실패와 구분되는지 확인한다.

**측정 장치를 붙이면 그 자체로 결함이 나온다.** CI를 만들자마자 로컬에서는 볼 방법이 없던
것이 드러났다. E2E도 같은 이유로 붙였다.

**절반은 실제로 돌려봐서 나왔다.** 코드를 읽어서 찾은 건 적다. 브라우저에서 클릭하고,
격리 스택에 요청을 보내고, 백엔드를 내려 봤다.
